### 7 结构同步与数据同步分离（2026-08-22）

按用户要求把两类同步彻底分开，设置页三类入口清晰：

| 类别 | 说明 | 触发方式 |
| :-- | :-- | :-- |
| 数据结构同步 | 对象/字段元数据（metadata + GraphQL schema 合并），结果缓存到本地（crmFieldMeta_v2_* + 版本/时间） | 初始化、结构版本升级时自动；手动按钮 |
| 数据记录同步 | 客户/联系人/机会等记录数据（fullPull） | 日常手动/定时 |
| 全量同步 | 结构 + 数据一起 | 手动按钮 / CRM 首页「全量同步」 |

- `CrmStructureSyncService`：结构版本（structureVersion）+ 上次同步时间持久化；

- 设置 → CRM 同步页同步卡片重构：测试连接 / 结构同步 / 数据同步 / 全量同步 / 对账，

### 8 联系人表排查：复合字段可读化（2026-08-22）

### 批次 10-2：定位残留线程 → 兜底移到 `FlutterWindow::MessageHandler`（已建）

- **用户实测**：残留线程只有主线程 `mood_diary.exe!ILT+5970(wWinMainCRTStartup)` = 主消息循环没退，引擎收尾被阻塞。

- 结合 Dart 侧 `didRequestAppExit` 清理（关库/停 Rust/取消同步）+ 3 秒 `exit(0)` 兜底：正常情况下资源释放后引擎收尾完成、快速干净退出；异常时也有 3s/8s 双层强制退出。

### 批次 10-4：`TerminateProcess`（真正根治）+ 禁用 WebView2 GPU（尽力而为）

**为何 `ExitProcess` 没用**：`ExitProcess` 仍会走 `RtlExitUserProcess → LdrShutdownProcess`，触发各 DLL 的 `DLL_PROCESS_DETACH`——`flutter_inappwebview_windows` 的静态 `GraphicsContext` 析构正是在此执行（释放 `IDirect3DDevice`），在部分 Intel/WebView2 环境卡死 `igd10um64xe.dll`。所以 `ExitProcess` 绕不开。

**修复（`windows/runner/main.cpp`）**：
- 主循环结束后改 `::TerminateProcess(GetCurrentProcess(), 0)`——**跳过 DLL 卸载（不跑 `DLL_PROCESS_DETACH`）**，插件静态 `GraphicsContext` 析构不会执行，D3D11 释放不会发生 → 进程立即、干净退出；
- 同时在 `wWinMain` 最开头 `SetEnvironmentVariableW("WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS","--disable-gpu")`（早于 Flutter/插件初始化，WebView2 惰性创建环境时读取），**尽力而为**关闭 WebView2 GPU，降低插件合成器 D3D11 设备的创建/释放风险。

> 坦诚说明：堆栈里的 D3D11 设备是**插件自身**用于合成 WebView 的 `GraphicsContext`（非 WebView2 渲染 GPU），`--disable-gpu` 主要关 WebView2 渲染，**不一定阻止插件建这个合成设备**；真正兜底是 `TerminateProcess`。两者叠加，退出可靠、快速。
