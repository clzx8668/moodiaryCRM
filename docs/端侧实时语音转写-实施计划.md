# 端侧实时语音转写（On-device Streaming ASR）实施计划

> 版本：v1（2026-09-21）　分支：`feat/align-get-brain`　负责人：主协调
> 目标一句话：**把"说完再上传云端识别"改成"边说边出字"**——本地 VAD 切句、
> 端侧模型推理、逐句上屏；云端转写退居"长录音/整篇格式化"的兜底。

---

## 1. 目标与验收

### 1.1 用户可感知目标

| 场景 | 现状 | 目标 |
| :-- | :-- | :-- |
| 语音速记（说 10-30 秒） | 说完 → 上传 → 等 3-30 秒（网络/模型慢时更久） | **说话过程中就出字**（句末 300ms 内补齐该句），不依赖网络 |
| 长录音（会议/访谈） | 只能整段上传转写 | 端侧先出草稿字幕；需要精修时再走云端整篇转写 |
| 无网络/无 API Key | 直接失败（只能在队列里等） | **端侧照常可用**（只要装了模型） |

### 1.2 工程验收标准

1. Android：录音过程中，输入框/字幕区能看到**逐句增量文本**（端侧，无网络请求）；
2. 端侧识别延迟：说话停顿后 **≤ 1 秒**出该句文本（中端机，int8 模型）；
3. 未安装端侧模型时：行为与现在一致（云端转写），并在设置里给出**可执行的引导**；
4. 端侧结果与云端结果**都不丢**：端侧草稿实时可见，云端（若配置）仍可整篇覆盖/校对；
5. `flutter analyze` 0 error、`flutter test` 全绿、Android 构建通过、真机走查通过。

## 2. 现状与瓶颈（代码实证）

- 语音入口：`VoiceCaptureController`（录音↔暂停↔停止）→ `PendingContentService.saveVoiceFast`
  → 队列任务 `voice_transcribe` → `LongAudioTranscribeService`（**整段上传**，`getAudioChat`/`multipart`）。
- 所以：**必须录完 → 上传 → 等模型返回**；期间用户看不到任何文字；失败时只能重试。
- 现有可复用资产：`record` 6.0.0（支持 **PCM 流** `startStream`）、
  `VoiceLevelWave/Envelope`（电平与包络）、`AiTaskQueueWorker`（异步任务）、
  `VoiceRecordMeta`（音频/转写/波形元数据）。

## 3. 方案选型（含本机实测约束）

### 3.1 本机/网络实测结论（2026-09-21）

| 项 | 结论 |
| :-- | :-- |
| crates.io | ✅ 可达（可拉纯 Rust 依赖） |
| github.com / raw.githubusercontent.com | ✅ 可达（可下预编译库与模型） |
| gitee.com | ✅ 可达 |
| modelscope.cn | ✅ 可达（中文模型生态） |
| huggingface.co / hf-mirror.com | ❌ 超时（**Whisper 官方权重拿不到**） |
| cmake / ninja | ❌ 本机未安装（whisper.cpp、sherpa-onnx 源码编译走不通） |
| Android NDK | ✅ 27.0 / 28.0 / 28.2 已装 |
| Rust 目标 | ✅ `aarch64-linux-android`、`x86_64-linux-android`、`x86_64-pc-windows-msvc` |

### 3.2 候选方案对比

| 方案 | 依赖 | 中文效果 | 实时性 | 本机可行性 |
| :-- | :-- | :-- | :-- | :-- |
| whisper.cpp / `whisper-rs` | 需 cmake 编译；模型在 HF ❌ | 中 | 自回归，慢 | ❌ 当前不可行 |
| candle + Whisper（纯 Rust） | 无 cmake | 中 | 自回归，慢 | ⚠️ 可行但模型要 HF/转换 |
| **sherpa-onnx 预编译 + Paraformer-zh-small int8** | 预编译库 + 模型（GitHub ✅） | **好（zh 原生，含中英混说）** | **非自回归，快** | ✅ **采用** |

### 3.3 采用方案（分平台，已实施）

```
麦克风 PCM(16k/mono/int16)
   └─► VAD(silero_vad.onnx, 端侧)         ← 判断"人声/静音"，只在人声段计算
         └─► 分段缓冲(句末静音 0.6s 或 段长 ≤ 20s)
               └─► 端侧识别(Paraformer-zh-small int8, 非自回归)
                     ├─ 段完成 → 上屏"终稿"文本（本地）
                     └─ 保存时：端侧终稿写入正文；若配置了云端语音模型 →
                        仍可整篇云端转写做精修（保留现有能力）
```

- **Android**：`sherpa-onnx-v1.13.8-android.tar.bz2`（44MB，含 `jniLibs/*.so` 与官方
  Kotlin API 源码）→ 编译进 App；用官方 `Vad + OfflineRecognizer` 组合（成熟配方，避免手写 C 结构体）。
  实现见 `android/.../AsrChannel.kt`。
- **Windows**：同版本 `win-x64-shared-MD-Release-no-tts`（18MB，内含 3 个 DLL）→
  **Rust + `libloading` 运行时加载 C API**（不手写 Dart FFI 结构体），
  经 flutter_rust_bridge 暴露 `asr_*` 接口给 Dart。实现见 `rust/src/asr_native.rs`
  \+ `rust/src/api/asr_bridge.rs`。

> 两端共用同一份 Dart 契约 `OnDeviceAsrEngine`，上层（语音面板/落地）完全不分平台。

### 3.4 模型与体积（实际采用）

| 文件 | 来源（本机可达） | 体积 | 说明 |
| :-- | :-- | :-- | :-- |
| `silero_vad.onnx` | GitHub `asr-models` release | 0.61MB | 语音活动检测 |
| `model.int8.onnx` + `tokens.txt` | `sherpa-onnx-paraformer-zh-small-2024-03-09`（官方包） | **78MB** | 中文非自回归，端侧 2 秒内出整句 |
| Windows 运行库 | 同上 release 的 win-x64 no-tts 包 | 19MB | `sherpa-onnx-c-api.dll` + `onnxruntime.dll`（+providers） |

> **为什么不用最初的 227MB large 模型**：实测在 x86_64 模拟器上加载到
> ONNX Runtime 建会话时**整进程静默退出**（无 tombstone、无 Java 异常），
> 真机上也更容易被系统回收。换 small 后同链路 2.09 秒跑通；云端精修仍作兜底。

> 模型不进 Git、不进安装包：**首次使用时下载/导入**，存于应用私有目录
> `…/asr/`（Android: `files/asr/`；Windows: `%APPDATA%/moodiary/asr/`）。

| **M4 接入语音面板** ✅ | 录音 PCM 流 → 门卫 → WAV + VAD 切句识别 → **实时字幕上屏**；停止后草稿直接落地 | 端侧链路 + 自动降级 + 落地草稿均有实现；面板字幕区已加 ✓ |

| **M6 收尾** ✅ | 设置页（状态/导入/**自检**）、降级路径、文档与提交 | analyze 0 error + test 604 全绿 + cargo test 全绿 ✓ |

### 尚未完成 / 后续可做

1. **Windows 图形界面端到端走查**：本机远程桌面处于息屏状态，无法截图佐证
   "点自检按钮出结果"；底层同一函数已用 `cargo test` 实测通过，
   但**建议在有屏的机器上点一次设置页的「运行端侧引擎自检」**确认 UI 呈现。
2. **Windows 录音侧 PCM 流**：`record` 插件在 Windows 上 `startStream(pcm16bits)`
   未实测；若该平台不支持，会返回错误并**自动回落**到原文件录音路径（不影响可用性）。
3. **实时流式模型**（真正的"逐词上屏"）：当前是"VAD 切句 → 整句上屏"，
   句末静音 0.3 秒后出字；要做逐字流式需换 streaming zipformer/paraformer。
4. **说话人分离 / 标点恢复**：sherpa-onnx 有现成模型，可作为后续增强。

### 每阶段固定动作

1. 先写"接口契约"（`AsrEngine` 抽象 + 事件模型），再实现；
2. 纯逻辑必须有单测；平台代码必须真机验证；
3. 每阶段：`flutter analyze` + `flutter test`（改 Rust 时 `cargo test`）；
4. 每阶段提交一次（`feat(asr): 批次xxx ...`），并在 `docs/开发进度.md` 记一段。

## 5. 平台差异（明确边界）

| 维度 | Android | Windows |
| :-- | :-- | :-- |
| 端侧推理 | **已实现**：jniLibs + 官方 Kotlin API（`asr_channel`） | **已实现**：Rust + C API（`libloading` 运行时加载）+ FRB 桥 |
| 音频采集 | `record.startStream` PCM 16k/mono | 同（Windows 走 WASAPI；不支持时自动回落文件录音） |
| 推理线程 | `numThreads=1`（模拟器/低端机更稳） | `numThreads=2` |
| 加速 | ARM NEON（arm64 默认开）；NNAPI 需 ONNX Runtime NNAPI EP，暂未接 | AVX2（onnxruntime 默认） |
| 模型体积 | int8 78MB | int8 78MB + 运行库 19MB |
| 运行库来源 | APK 内 `jniLibs/{arm64-v8a,x86_64}` | `%APPDATA%\cn.yooss\moodiary\asr\` 下 3 个 DLL |
| 降级 | 无模型 → 云端转写（现状） | 本批先保持云端 |

## 6. 与现有链路的关系（不推翻已有设计）

1. **先落地不变**：录音仍立即写本地文件；端侧字幕是"额外增量"，不影响落库；
2. **云端转写保留**：`voice_transcribe` 任务继续存在；端侧只负责"实时可见的草稿"，
   云端（若配置）仍可产出"整篇精修稿"；两者都写 `VoiceRecordMeta`（新增 `onDevice` 标记区分来源）；
3. **失败可观测**：端侧失败 → 字幕区提示原因（模型缺失/初始化失败），队列里仍可重试云端；
4. **模型缺失不阻塞**：没有模型 = 现在的能力（纯云端），设置页给一键下载入口。

## 7. 风险与备选

| 风险 | 应对 |
| :-- | :-- |
| 模型下载慢/失败（78MB+） | 脚本断点友好；支持手动导入；下载失败时保持云端路径 |
| Kotlin API 与 .so 版本不匹配 | 用同一 release 的 lib + kotlin-api 源码；版本号锁定在 `tool/fetch_asr_model.ps1` |
| 端侧识别质量不如云端（专有名词） | 端侧出草稿、云端可覆盖；`VoiceRecordMeta` 保留两份文本 |
| 中低端机推理偏慢 | int8 + 段长限制（≤20s）+ 只对 VAD 人声段推理；必要时降到 8k 采样或换更小模型 |
| ONNX Runtime 在部分 ABI 缺失 | 只打包 `arm64-v8a`（真机）+ `x86_64`（模拟器）两种 |
