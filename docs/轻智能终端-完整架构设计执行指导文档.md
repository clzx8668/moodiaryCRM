# 轻智能终端 (Moodiary) 架构设计执行指导文档

本文档为项目的 ARCHITECTURE.md，覆盖产品定位、架构设计、数据结构、Rust 层模型、同步引擎、前端状态管理、测试策略、工程实践等全链路设计。Flutter 与 Rust 开发团队可直接对照使用。

---

## 一、全局架构设计规则 (Design Rules)

1. **双模态数据协议**：所有模块数据底层统一采用 Block 协议（JSON 数组）。文本内容使用 Markdown 格式存储，实体数据（如 CRM 联系人、待办事项）使用结构化 JSON 存储，确保数据表达的一致性与灵活性。

2. **数据与文件解耦**：附件管理全面采用 Obsidian 模式，本地文件按文件夹归档存储。数据库仅保存文件的相对路径，跨端文件同步通过 WebDAV 协议独立进行，避免数据库体积膨胀。

3. **本地优先与乐观更新**：所有写入操作优先落盘至本地 Isar 数据库，UI 层实现瞬间响应。联网状态下，由 Rust 同步引擎基于时间戳进行增量双向同步，保障离线可用性。

4. **业务与检索分离**：Isar 数据库负责业务数据的精确查询与状态管理；向量检索（RAG）交由独立的本地向量库（如 LanceDB）处理，两者通过 Block ID 进行关联，实现结构化与语义检索的解耦。

5. **模块化开关**：所有非核心模块（如 CRM、知识库）在设置中提供独立的功能开关。关闭后，系统不加载对应路由与后台任务，降低资源占用。

6. **页面级差异化操作入口**：摒弃全局统一的 FAB 按钮，改为每个页面根据自身业务场景配置独立的浮动操作按钮。各页面 FAB 风格保持统一（圆角、阴影、主色调），但功能与交互模式因页面而异——首页为"快速收集"、日历为"快速建日程"、CRM 为"新增客户"、知识库为"常驻 AI 对话输入框"、设置页不设 FAB。所有 FAB 的交互面板参照当前最流行的同类产品设计范式，确保操作直觉性与效率。

7. **特性开关与编译优化（Feature Flags）**：
   - **编译期开关（Cargo Features）**：对于 LanceDB 等大型原生依赖，设计为 Cargo Feature。用户不需要知识库功能时，可在编译时直接剔除对应代码，显著减小安装包体积。
   - **运行时开关**：对于 CRM、日历等功能，通过读取本地配置决定是否初始化后台同步任务，比单纯隐藏 UI 更能节省电量和内存。

8. **状态管理分层原则**：每个功能模块的状态管理器必须独立、细粒度，禁止将多个模块的状态耦合到同一个 Provider 或 State 中。特别是中间详情页（SmartCanvasPage），必须采用独立的状态管理架构（详见"二、五大核心模块详细规划 — 中间详情页状态管理设计"）。

## 二、五大核心模块详细规划

### 1. 首页：记录列表 + 快速收集 + 搜索查询

**定位**：信息捕获的漏斗与日常回顾的起点。

- **快速记录收集（首页 FAB 按钮）**：FAB 按钮位于右下角，点击唤起底部半屏收集面板。面板顶部为文本速记输入区，支持富文本格式；面板底部提供附件添加按钮（图片、文档、PDF 等），附件以缩略图形式展示并可预览；语音输入功能预留交互入口（麦克风图标），待后续接入语音识别引擎。速记内容保存时，Rust 层在后台静默进行意图识别，自动为内容打上临时 Tag。
- **AI 预处理**：速记内容保存时，Rust 层在后台静默进行意图识别，自动为内容打上临时 Tag，等待用户在中间详情页进行结构化确认。
- **记录列表**：支持按时间线、标签、心情等多维度筛选，并提供"块视图"切换功能，以卡片流形式展示 AI 提取的核心摘要和关键实体。
- **全局搜索**：基于 Rust Jieba 分词实现全文检索，支持跨模块数据查询（日记、CRM 客户名、知识库概念）。

### 2. 日历模块：热力图 + 待办 + 日常安排

**定位**：时间维度的数据可视化与行动管理。

- **日历热力图**：根据每日记录字数、Block 数量及心情指数，渲染不同深浅的颜色以直观展示活跃度。
- **待办与日程**：聚合首页记录中由 AI 提取的 Todo 块，以及 Twenty CRM 的 Tasks 对象。
- **时间轴视图**：将当天日记、待办事项、CRM 沟通记录按时间戳串联展示。
- **日历 FAB 按钮**：点击后唤起快速新建面板，参照主流日历应用（如 Google Calendar、滴答清单）的快捷添加设计——面板顶部为标题输入框，下方为日期/时间选择器（支持"今天""明天""自定义"快捷选项）、重复规则选择、提醒时间设置，底部为保存按钮。用户可在 3 步内完成日程或待办的创建，无需跳转独立页面。

### 3. CRM 模块：业务映射与自定义视图

**定位**：轻量级客户关系与业务跟进中枢。

- **数据映射与同步**：通过 Rust 引擎与 Twenty CRM 的 Companies、People、Opportunities 进行双向增量同步。
- **自定义显示表格**：用户可自定义列表页显示字段，前端根据配置 JSON 动态生成 Data Table，支持按列排序和筛选。
- **业务详情下钻**：通过 diary_uuid 关联拉取该客户在 Moodiary 中的所有相关日记，实现"以人为中心"的上下文聚合。
- **CRM FAB 按钮**：点击后唤起快速新建客户面板，面板包含客户名称、公司、联系方式等核心字段的快速填写表单，支持从首页记录中 AI 已提取的实体信息自动填充（若存在匹配记录）。保存后自动触发与 Twenty CRM 的增量同步。

### 4. 知识库模块：RAG 检索与 AI 对话

**定位**：个人数字资产的结构化沉淀与智能问答。

- **知识库管理**：支持创建多个独立知识空间，并提供批量归档功能。
- **向量化引擎**：Rust 层调用 Embedding 模型生成向量并存入 LanceDB，支持增量索引。
- **AI 对话工作台**：提供知识库选择器，AI 回答附带引用的 Block 来源卡片，实现引用溯源。
- **知识库 FAB 按钮**：不设传统 FAB，采用常驻式 AI 对话输入框设计，参照当前最流行的 AI 工具交互范式（如 ChatGPT、Claude、Perplexity）。输入框固定于页面底部，顶部为知识库选择器（下拉菜单选择当前对话关联的知识库），用户输入问题后 AI 以流式方式返回回答，并附带引用溯源卡片。该输入框始终可见、始终可用，形成思考与获取答案的无缝闭环。

### 5. 设置模块：功能开关与配置中心

**定位**：应用的控制中心，保持轻量与克制。

- **基础设置**：包含主题、字体、WebDAV 同步配置、密码与生物识别等。
- **模块功能开关**：提供 CRM、知识库、日历模块的独立启用/禁用开关。关闭某模块后，首页导航栏隐藏对应 Tab，后台停止相关的同步与索引任务。
- **数据与存储管理**：展示本地 Isar 数据库大小、LanceDB 向量库大小、附件文件夹大小。提供"一键清理孤立附件"、"重建向量索引"等高级维护工具。
- **同步日志入口**：提供"同步日志"查看页面，展示 Rust 层记录的同步成功/失败详情（含错误原因、时间戳），方便开发调试和用户使用中快速定位问题。
- **数据健康度检查工具**：
  - **附件扫描**：扫描 /Attachments/ 目录，找出未被任何 Block 引用的"孤立文件"，提供一键清理功能。
  - **索引重建**：提供"重建向量索引"按钮，强制 LanceDB 与 Isar 中的 Text Block 进行全量对齐。
  - **同步对账**：提供高级选项，触发一次与 Twenty CRM 的全量数据对账（而非增量），修复因极端情况导致的数据偏差。
- **设置页不设 FAB 按钮**：设置模块为配置型页面，所有操作通过列表项完成，无需额外的浮动操作入口。

### 6. 中间详情页（SmartCanvasPage）状态管理设计

**定位**：整个应用最复杂的 UI 组件，负责流式渲染、原位编辑、下拉搜索等多种交互。

#### 6.1 设计原则

- **禁止**将所有状态塞进一个巨大的 State 或 Provider 中。
- 必须为 SmartCanvasPage 设计一个**独立的、细粒度的状态管理器**（推荐使用 GetX 的独立 Controller 或 Riverpod 的独立 StateNotifier）。
- 将不同维度的状态**分离管理**，避免局部刷新导致整个列表重绘卡顿。

#### 6.2 状态分层架构

| 状态层 | 职责 | 状态内容 | 更新触发 |
| :--- | :--- | :--- | :--- |
| **BlockListState** | 管理原始 Block 列表 | List<Block> 完整列表、排序、分页 | 数据加载、同步拉取、用户编辑 |
| **StreamingState** | 管理 AI 流式输出 | 当前流式 Block ID、累积文本缓存、流式进度 | Rust 层 SSE 推送 |
| **EditState** | 管理当前编辑状态 | 当前正在编辑的 Block ID、编辑模式（预览/编辑）、原位编辑的临时值 | 用户点击编辑、输入 |
| **SearchState** | 管理搜索过滤 | 搜索关键词、过滤后的 Block ID 集合 | 用户输入搜索词 |
| **SyncState** | 管理同步状态 | 同步进行中/完成/错误、错误信息 | Rust 层事件总线 |

#### 6.3 状态隔离与局部刷新策略

- **BlockListState** 负责渲染 ListView.builder 的每一项。当某个 Block 被编辑时，仅通过 setState 或状态通知更新该 Block 对应的 Widget，利用 ListView.builder 的虚拟化特性，未变化的行不会重绘。
- **StreamingState** 独立于 BlockListState。AI 流式输出时，流式文本仅更新 StreamingState 中的缓存，通过 ValueListenableBuilder 或 GetX 的 Obx 仅刷新流式输出区域，不影响列表其他项。
- **EditState** 管理原位编辑时，仅当用户点击某个 Block 的编辑按钮时，该 Block 切换为编辑模式（显示输入框），其他 Block 保持预览模式。编辑完成后，通过 BlockListState 的局部更新方法替换该 Block 的内容。
- **SearchState** 与 BlockListState 解耦。搜索时，SearchState 仅维护过滤后的 Block ID 集合，BlockListState 根据该集合决定渲染哪些行。搜索词变化不会导致列表全量重绘。

#### 6.4 AI 流式状态可恢复设计

AI 流式输出是用户体验的关键，但也是最容易出问题的地方（如网络中断、App 被系统杀死）。

- **stream_buffer 字段**：在 Isar 的 Block 模型中，为 ai_stream 类型的 Block 增加 stream_buffer 字段（String 类型），用于持久化流式输出的中间状态。
- **Rust 层写入策略**：Rust 层在接收到 AI 的每一个 Token 时，除了通过 FFI 推送给 Flutter 渲染，还应定期（如每 50 个 Token）将累积的文本追加写入 stream_buffer。
- **Flutter 层恢复策略**：当用户重新打开 App 或从后台恢复时，UI 首先从 Isar 中读取 stream_buffer，恢复已接收的内容并渲染。同时检查该 Block 的 stream_complete 标记：若未标记为完成，则通过 FFI 通知 Rust 层继续请求 AI 补全剩余内容。
- **防重复请求**：恢复时通过比较 stream_buffer 中的最后写入位置与 AI 服务的响应位置，避免重复发送已接收的 Token。

### 3.2 LanceDB 向量表设计 (vector_store.rs)

- **表名**：block_embeddings
- **列定义**：
  - block_id: String (主键，关联 Isar Block.id)
  - text_content: String (用于重新生成向量的文本快照)
  - embedding: Vector (向量，维度由 Embedding 模型决定，如 768)
  - metadata: String (JSON 字符串，包含 diary_id, block_type, source 等)
  - created_at: i64
- **索引策略**：HNSW 索引，支持近似最近邻搜索 (ANN)。
- **增量更新策略**：当 Block 被修改时，先删除旧向量再插入新向量。

### 3.4 数据迁移脚本设计 (migration.rs)

由于从单一的 content 字符串升级为 blocks 数组是破坏性数据库结构变更，必须在 App 启动时自动处理历史数据迁移：

- **版本检测**：在 Isar 数据库初始化时，读取 app_metadata 表中的 db_version 字段。若当前代码版本期望的 db_version 高于存储版本，则按版本号顺序执行迁移脚本。
- **迁移逻辑（v1 → v2）**：
  1. 读取所有旧版 Diary 记录的 content 字段。
  2. 将每个 content 字符串包装为一个 text 类型的 Block：{"id": uuid, "type": "text", "content": <原content值>}。
  3. 将生成的 Block JSON 数组写入新版 blocks 字段。
  4. 清除旧版 content 字段（或标记为已迁移）。
  5. 更新 db_version 为当前版本。
- **增量迁移**：每次数据库结构变更时，编写从 current_version 到 current_version + 1 的增量迁移脚本，确保迁移过程可追溯、可回滚。
- **迁移日志**：每次迁移执行后，在 SyncState 表中记录 migration_history 条目（迁移前版本、迁移后版本、迁移时间、耗时），方便排查迁移失败问题。

## 四、Rust 层同步引擎接口设计

### 4.1 同步引擎核心接口 (sync_engine.rs)

```rust
pub trait SyncEngine {
    /// 初始化同步引擎，加载 SyncState
    async fn initialize(&self) -> Result<()>;

    /// 触发全量同步（用户手动）
    async fn full_sync(&self) -> Result<()>;

    /// 自动检测是否需要增量同步
    async fn auto_sync_if_needed(&self) -> Result<()>;

    /// 返回当前同步状态
    async fn get_sync_status(&self) -> Result<SyncStatus>;

    /// 取消正在进行的同步
    async fn cancel_sync(&self) -> Result<()>;
}
```

### 4.2 增量拉取引擎 (pull_engine.rs)

```rust
pub trait PullEngine {
    /// 拉取 Diary 变更
    async fn pull_diary_changes(&self, since_timestamp: i64) -> Result<Vec<DiaryChange>>;

    /// 拉取指定日记下所有变更的 Block
    async fn pull_block_changes(&self, diary_uuid: String, since_timestamp: i64) -> Result<Vec<BlockChange>>;

    /// 拉取 CRM 实体完整/增量数据
    async fn pull_crm_entities(&self) -> Result<Vec<CrmEntity>>;

    /// 解决拉取冲突 (Last Write Wins)
    fn resolve_pull_conflict(&self, local: Diary, remote: Diary) -> Diary;
}
```

### 4.8 同步引擎错误处理与日志设计 (sync_logging.rs)

Rust 层的同步引擎需要在后台静默运行，一旦出错，用户在前端是感知不到的，这会导致数据不一致。因此必须建立完善的错误处理与日志体系：

- **本地日志文件**：在应用沙盒中创建 logs/sync.log 文件，所有同步操作（成功/失败/警告）均追加写入。日志格式采用结构化 JSON，包含字段：timestamp, level (INFO/WARN/ERROR), operation (pull/push/upload/download), target (diary/block/file/crm), detail (具体描述), error (错误堆栈/原因)。
- **错误分级**：
  - **WARN**：可自动恢复的临时错误（如网络抖动重试成功），仅记录日志，不通知用户。
  - **ERROR**：不可自动恢复的错误（如 WebDAV 连接超时、Twenty API 返回 500），记录日志的同时更新 Isar 中对应记录的 sync_status 为 error，并在设置页的"同步日志"中展示。
- **同步日志查看**：在设置页提供"同步日志"入口，以列表形式展示最近 500 条日志，支持按级别筛选（全部/警告/错误）、按时间范围筛选、一键清空。
- **错误恢复机制**：对于可重试的错误（如网络超时），实现指数退避重试策略（初始延迟 1s，最大重试 5 次，每次延迟翻倍），重试成功后将 sync_status 更新为 synced 并清除错误信息。

### 4.9 Twenty API 限流与缓存策略 (rate_limit.rs)

Twenty CRM 是自托管服务，但移动端网络环境复杂，频繁的全量或增量请求可能造成不必要的负载。

- **防抖（Debounce）**：用户快速连续修改多条日记时，不要立即触发推送，而是等待用户停止操作 2 秒后合并为 1 次批量推送。
- **指数退避（Exponential Backoff）**：当 API 返回 429（Too Many Requests）或 5xx 错误时，首次重试等待 2 秒，第二次 4 秒，第三次 8 秒，以此类推，最大等待 60 秒，最多重试 5 次。
- **读取缓存**：对于 CRM 的客户列表等读多写少的数据，在本地 Isar 做好缓存。UI 优先展示本地缓存数据，后台静默发起增量刷新。缓存过期时间可配置（默认 5 分钟）。
- **请求合并**：在防抖窗口内，同一日记的多次修改合并为 1 次 PUT 请求，仅推送最终状态，减少 API 调用次数。

## 五、前端与 Rust 层交互协议

### 5.1 FFI 接口设计

- 所有 Rust 耗时操作通过 async/await 暴露给 Flutter（通过 flutter_rust_bridge）。
- 使用 EventStream 推送同步进度和 AI 流式输出。
- 错误处理统一通过 Result 类型包装，Flutter 层负责展示用户友好的错误提示。

### 5.2 FFI 契约设计规范

由于核心逻辑在 Rust，UI 在 Flutter，两者之间的通信（通常通过 flutter_rust_bridge）是性能瓶颈和 Bug 的高发区，必须建立严格的 FFI 契约：

- **接口定义先行**：在编写具体业务前，先定义好 Rust 端暴露给 Flutter 的所有 Trait 接口和数据结构（Struct/Enum）。将接口定义写入独立的 .rs 文件（如 ffi_api.rs），作为双方通信的"合同"。
- **数据结构扁平化**：Rust 返回给 Flutter 的数据结构尽量扁平化，避免在 FFI 层传递过于复杂的嵌套对象。对于深层嵌套的数据，拆分为多个扁平的响应结构，通过 ID 关联。
- **序列化优化**：优先使用 bincode 而非 serde_json 进行 FFI 序列化/反序列化，性能提升显著（二进制格式比 JSON 快 5-10 倍，且体积更小）。
- **版本化**：所有 FFI 接口增加 api_version 字段。当接口发生破坏性变更时，升级版本号，Rust 层根据客户端版本号路由到不同的处理逻辑，保证向后兼容。

### 5.3 事件总线设计

- **SyncProgressEvent**：{ type: "started"|"pulling"|"pushing"|"uploading"|"done"|"error", progress: f32, message: String }
- **AiStreamEvent**：{ block_id: String, chunk: String, is_complete: bool }
- **FileSyncEvent**：{ file_path: String, status: "uploading"|"downloaded"|"error", progress: f32 }

## 七、多引擎同步策略

- **结构化数据流**：Flutter UI → Isar → Rust Sync Engine → Twenty CRM API
- **文件资产流**：Flutter UI → 本地沙盒 → Rust WebDAV Engine → 远端 WebDAV/MinIO

### 7.1 向量库懒加载策略

虽然架构规划中引入了 LanceDB，但在项目初期（Phase 1 & 2），数据量很小，完全不需要急着集成。

- **接口预留**：在 Rust 层预先定义好 VectorIndex 的 Trait 接口（见"四、4.7"），但在代码实现上先用"空实现（Mock）"占位，所有方法返回 Ok(()) 或空结果。
- **编译期控制**：将 LanceDB 依赖设计为 Cargo Feature（如 feature = ["vector-db"]）。默认不启用，用户不需要知识库功能时，编译时直接剔除，避免引入过多的原生依赖导致编译时间变长和调试困难。
- **平滑切换**：等到 Phase 3 真正需要知识库功能时，只需实现 VectorIndex trait（将 Mock 替换为 LanceDB 的真实实现），并启用对应的 Cargo Feature，无需修改任何调用方代码（依赖倒置原则）。

## 九、二次开发与扩展点设计

项目基于开源 Moodiary 进行二次开发，未来可能会升级上游代码或开源自己的版本。为确保可维护性，需在代码组织上做好隔离：

### 9.1 目录隔离

在 Flutter 端，将自定义模块与上游代码进行物理隔离：

- 新增的 SmartCanvasPage、CrmModule、KnowledgeBaseModule 等放在独立的 lib/features/ 或 lib/custom/ 目录下，而不是散落在上游的 lib/pages/ 中。
- 上游核心文件（如路由注册、主题配置）通过"扩展点"机制注入自定义逻辑，而非直接修改上游源码。

### 9.2 接口抽象

对于需要与上游代码交互的地方，尽量通过接口或回调的方式进行：

- **路由注册**：定义统一的 RouteRegistry trait，上游提供基础路由，自定义模块通过扩展点注册自己的路由。
- **主题注入**：定义 ThemeExtension trait，自定义模块提供自己的主题色、圆角等配置，在 App 启动时注入。
- **设置项扩展**：定义 SettingsProvider trait，自定义模块在设置页中追加自己的配置项，无需修改上游设置页代码。

### 9.3 版本兼容性

- 在 pubspec.yaml 中锁定上游 Moodiary 的依赖版本，并记录上游 commit hash，便于追踪上游变更。
- 每次升级上游版本前，先运行完整的测试套件，确认无破坏性变更后再合并。

## 十二、对标得到大脑的演进补充（2026-09-05）

> 本补充源于「得到大脑（原 Get 笔记）」对标分析，落地路线见
> 《对标得到大脑-产品闭环与开发指导.md》；此处只记录架构层约定，不在本文档重复产品细节。

### 12.1 产品定位与主循环

- **定位**：本地优先的「AI 第二大脑 + CRM」；产品主循环为
  **收集 → AI 整理 → 主动思考 → 智能找回 → 创作输出 → 落地行动（CRM/日程）**；
- 页面与模块应能回答“服务于主循环的哪一环”，无法回答的新增需求不进入开发。

### 12.2 捕获类型元数据（captureType）

Block `metaJson` 预留以下字段（不进 Drift schema，除非演进需要）：

```json
{
  "captureType": "text | voice | photo | link | document | meeting",
  "sourceUrl": "原文链接（可选）",
  "sourceTitle": "原始标题/作者（可选）",
  "originalTranscript": "语音/OCR 原始转写（可选，与清洗稿分离）"
}
```

- 原文、转写、清洗稿三层保留原则：原文永不静默替换；
- 采集正文/图片落入本地附件体系，数据库只存相对路径 + `sourceUrl` 溯源。

### 12.3 AI 技能注册表（点评/发芽/拷问/打磨）

- 在既有 AI 模板能力上扩展注册表，模板产物一律进入 AI 生成区
  （`source=ai` 新块），不原位改写原文；
- 新增技能与语义：

| 技能 | 语义 | 产物 |
| :-- | :-- | :-- |
| 点评 | 旁观者视角找亮点与盲区 | AI 区评论块（可回看） |
| 发芽 | 从一条记录延伸新想法 | AI 区新块，可“一键新建”为笔记 |
| 拷问 | 苏格拉底式追问 | AI 区新块，支持逐条回答成对话 |
| 打磨/成稿 | 把话说成可发布作品 | 作品草稿（WORKS 层），可版本归档 |

- 去口语化是唯一“原位 + 原文可切回”例外；打磨成稿与去口语化职责分离。

### 12.4 作品层（WORKS）与周期回望（DIGEST）

- **WORKS**：选定 1-N 条记录 → 按公众号/小红书/工作汇报等格式起草 → 复用全局
  Markdown 编辑器 → 版本归档 → 导出/分享；产物不混入主日记流；
- **DIGEST**：按日/周静默生成跨记录汇总（数量/话题/待办/建议），作为可归档回望条目。

### 12.5 主题集合与个性化画像

- 在现有 `KnowledgeBases` 之上增加轻量主题集合（多对多引用各类内容），不建第二套知识库；
- 设置内维护轻量「专业词库/常用表达/偏好」JSON，注入润色与技能 Prompt；
- 主动建议统一挂在 `AiTaskQueueWorker` 任务完成出口，不另起通知链路。
